# Reader (M6 Bidirectional Reader)

[中文](./reader.md) | [English](./reader.en.md)

The bidirectional-jump architecture lives in [`document-architecture.en.md`](document-architecture.en.md) §32–33. This page documents the current implementation: viewer data contract v2, the frontend spatial index, navigation/scroll/highlight/focus behavior, the Semantic Inspector, the console surfaces, the reader API, and local re-rendering.

## Viewer data contract v2

`pdf_pipeline.pipeline._write_viewer_assets` is the only producer of the `viewerDataVersion: 2` package. Each publish first writes a complete immutable `revisions/<id>/` directory (`mapping.json`, `viewer-meta.json`, `source.pdf`, `target.pdf`), then replaces the stable aliases and rerendered workspace JSON as a recoverable file set, and atomically replaces `manifest.json` last. A mid-commit failure restores every replaced file and removes the unpublished revision. The reader loads all URLs from one manifest as a group; only initial boot without a manifest uses all stable aliases together, with no per-file fallback. The Vite `serve-public-data` plugin serves `/data/*` from `public/data` on every request so those paths never hit the SPA fallback. Canonical MappingBundle fields expand as before (the `mapping` schema stays at 0.1.0, zero changes), plus a viewer-private projection:

| Key | Contents |
| --- | --- |
| `semanticNodes` | all nodes (root skipped): `id/kind/parentId/content/confidence/provenanceIds`; content and confidence are canonical dumps |
| `semanticRelations` | full `semantic.relations` |
| `sourceRegions` | `{id, pageIndex, geometry}` (unchanged) |
| `renderAnchors` | RenderAnchor dumps (geometry stays in the viewer package, never in canonical mapping — see the [M2 note](../../.agents/notes/implemented/architecture/2026-09-04-m2-walking-skeleton.en.md)) |
| `translation` | `{targetLocale, sourceLocale?, providerModel?, terminologyRevision?, terminology?, entries[{semanticNodeId, content, confidence?, providerModel?, cacheKey?}]}` |
| `provenance` | `semantic.provenance.records` |
| `issues` | concatenation of semantic + mapping + translation IssueStore.issues |

`viewer-meta.json` carries per-page size arrays `sourcePages` / `targetPages` (`{widthPt, heightPt}[]`): scroll sync and any page geometry lookup must use the real per-page size, never page 0's.

`run_pipeline` also copies the input bytes to `source.pdf` in the workspace so `rerender_workspace` needs no user re-upload.

## Spatial index (6.1/6.2)

`apps/web/src/spatial.ts::PageSpatialIndex` is a frontend per-page uniform grid (8 columns × 12 rows; cell size comes from that page's meta, missing pages fall back to the first known size on the same side):

- a fragment registers into every cell its rect covers; point and band queries gather deduplicated cell candidates, then exact rect-test them.
- `hitTest(page, x, y)`: fragments containing the point, ascending by area. `inBand(page, yMin, yMax)`: fragments intersecting the horizontal band, ascending by rect.y. Zero-area rects and unknown pages return empty, never throw.
- Paper-scale fragment counts stay < 10³, so cell lookup is O(1); a dense cell still scans its candidates. A real R-tree can replace the internals behind the same interface (see the [M6 note](../../.agents/notes/implemented/feature/2026-09-11-m6-bidirectional-reader.en.md)).

## Navigation behavior (6.3/6.4)

`Pair = { sources: Fragment[]; targets: Fragment[] }` in `apps/web/src/mapping.ts` collects every fragment on both sides (multi-fragment is first-class). Node identity comes from bindings. `pickCounterpart(pair, origin, originRect)` is the Initial Product **intra-node landing heuristic** (the PRD does not require character-level mapping): among counterpart fragments on the smallest page at/after the origin page, the closest y; when none exists at/after, the first counterpart. It does not decide FR-SYNC-004 identity. Pointer clicks go through spatial-index `hitTest` (smallest area first); keyboard activation still uses the focused button's fragment.

`activate(nodeId, origin, fragment)` in `apps/web/src/reader.ts` (`DualPaneReader`):

1. render the destination pane on the `pickCounterpart` page (each side's `PaneRenderer` cancels the previous PDF.js task and commits only the latest generation; a same-page request also invalidates an uncommitted older page turn before redrawing the overlay);
2. scroll that fragment to the vertical center of the pane viewport via `(fragment midline pt / page height pt) × container.scrollHeight` (clamped; after fit-width the canvas pixel height is no longer known — see "Console surfaces");
3. `focus({preventScroll:true})` the destination overlay button;
4. the origin side redraws keeping its `aria-pressed` selection; the active state survives page turns. Selection updates go through `setActiveNode` so the overlay and Inspector stay in sync.

Sync scroll (`#sync-scroll` checkbox, off by default): a ±12 pt band around the scrolling pane's viewport midline goes through `inBand` → first hit with a paired node → `pickCounterpart` → the other side renders and scrolls into place; the midline comes from `(scrollTop + clientHeight / 2) / scrollHeight × page height pt` (fit-width ratio math, not canvas pixels). When no node is found, nothing happens (page-number-guess fallbacks are forbidden). Programmatic scrolls suppress the opposite side's scroll events for 250 ms to break loops.

## Semantic Inspector (6.5)

`apps/web/src/inspector.ts::renderInspector(root, model, nodeId, opts)`. Stable ids double as e2e selectors: `#inspector-node-id` (full SemanticNodeID), `#inspector-kind`, `#inspector-anchors` (per-side `source p{n} [x,y w×h]` lines), `#inspector-source-text`, `#inspector-translation` (`Not translatable` when there is no entry — BIBLIOGRAPHY_ENTRY is deliberately not translated per PRD FR-CITE-004), `#inspector-relations` (two-way relation buttons jump), `#inspector-confidence` (node score + reason + target anchor confidence), `#inspector-provenance`, `#inspector-issues` (only when non-empty), `#inspector-terminology`, `#inspector-citations` (six reference mark types sliced from source/translation text at Unicode code-point offsets with jumpable `targetNodeId`; out-of-range marks render `mark out of range` without throwing). Viewing original vs. translation is the two-pane reading itself; no pane content switching. `#inspector` is the last card of the floating `#surface-panels` column and is shown or hidden by `#inspector-toggle` (a checkbox, checked by default): unchecking hides it, and with no selected node the panel stays `hidden`. It floats above the PDFs and consumes no display width.

## Reader API and local re-render (6.6)

`apps/api` (stdlib ThreadingHTTPServer, no web framework):

- `GET /api/health` — same payload as `/health`; the frontend probes at startup and only renders `#retranslate-button` when `apiAvailable`.
- `POST /api/retranslate` selects the workspace from the current revision binding and uses a cross-process workspace lock. Requests, status codes, and legacy compatibility are in [HTTP API](api.en.md#retranslation-document-binding); lock ordering is in [storage](storage.en.md#m8-p1-concurrency-repairs).

`pdf_pipeline.pipeline.rerender_workspace(workspace_dir, viewer_data_dir=…, node_ids=…)` (FR-TRANS-004: zero source-PDF re-parsing): load the six canonical workspace documents → validate `node_ids ⊆ translation.entries` keys → `retranslate_nodes` with the **current** provider identity (selected nodes skip cache reads) → compose → LaTeX projection + staged compile → `recover_render_anchors` → rebuild the MappingBundle reusing the source-side bindings from the old mapping → write the immutable viewer revision after validation, then commit stable aliases, the three workspace JSON files, and the manifest with rollback protection. A real workspace with no provider configured fails rather than falling back to dummy. Note that re-projecting recompiles the whole target document (seconds to tens of seconds); concentrating that cost in one compile is intentional.

Frontend wiring: the Vite `dev` and preview servers proxy `/api` to `:8000` and serve `/data/*` from `public/data` per request (the data root moves to the resolved `PAPER_VIEWER_DATA_DIR` when that env is set — used by the batch-F publish-failure e2e to serve a copy of the fixture data; unset means byte-identical default behavior). `just serve-reader` starts the three-process local stack — API, `paper_worker --jobs-root .jobs`, and Vite — and the Playwright webServer mirrors the exact same command. `main.ts` only boots the app (`bootSurfaceTabs()` after `reader.start()`, then `bootImportPanel(reader)` / `bootSelectPanel(reader, tabs)` / `bootHistoryPanel(reader, tabs)` / `bootStatusPanel(reader, tabs)`); `DualPaneReader` owns pane lifecycle, navigation, and retranslate state. After a successful retranslate the reader loads candidate mapping/meta/PDF as one group from the new manifest and only then swaps, destroying the old target document. A load failure keeps the previous reading state; if the candidate's first render fails after the swap, the reader redraws the old target page and restores page chrome, overlay, focus, and scroll positions. Status line `Node re-translated · <first 8 chars> · <revision 8 chars>`; `#viewer` `data-busy` / `data-revision` let e2e wait for busy→idle.

Correctness repairs: [M6 review repairs](../../.agents/notes/implemented/bug-fix/2026-09-11-m6-review-repairs.en.md).

## Console surfaces

`#surface-tabs` in `apps/web/index.html` holds four `role="tab"` buttons (`#tab-upload` / `#tab-select` / `#tab-history` / `#tab-status`), each controlling one `role="tabpanel"` inside `#surface-panels` (`#panel-upload` / `#panel-select` / `#panel-history` / `#panel-status`). `apps/web/src/surface-tabs.ts::bootSurfaceTabs()` is the single source of state: clicking a surface that is not open calls `open(id)`, clicking the one already open calls `close()` (every panel `hidden`, every tab `aria-selected="false"`), so at most one tab panel is visible at a time; `onChange` subscribers refresh their list or start and stop polling. The same tab bar carries two checkboxes: `#sync-scroll` (sync scroll, off by default) and `#inspector-toggle` (region info, checked by default, see 6.5).

Layout (`viewer.css`): `#reader-body` is the positioning context and `#panes` is a two-column grid; each `.page-scroll` scrolls vertically only (`max-height: 72vh`) and `.page-stage canvas` is `width: 100%; height: auto`, so both PDFs always scale to the column width (fit-width) and never produce a horizontal scrollbar; the `1 / N` page number and Previous/Next sit in the `.page-controls` box pinned to each pane's bottom-right corner (`#source-page` / `#target-page`). `#surface-panels` is an **absolutely positioned right-hand floating drawer** (`top: 0; right: 0; bottom: 3.5rem; width: min(360px, 34vw)`, `z-index: 6`, container `pointer-events: none`, cards `pointer-events: auto`): the tab panels and region info share that one column, whose DOM order is fixed to upload → select → history → status → `#inspector`, so a tab panel always renders above the region info card when both are visible. The drawer **never consumes PDF display width**; its price is covering regions at the right edge of the right pane — e2e specs that must click a region therefore `uncheck("#inspector-toggle")` first (product behavior is unchanged). `bottom: 3.5rem` parks the drawer above the page controls so `#source-next` / `#target-next` stay clickable.

Visual layer (the `:root` block of the same file): the palette is copied value for value from Overleaf's published stylesheet (`https://cdn.overleaf.com/stylesheets/main-style-476eb7ca577de65f3a7b.css`, fetched 2026-09-17) with the upstream token names; it is the single source of color in `viewer.css` — an `#rrggbb` literal is allowed only inside that block, everything else is `var(--…)` or an `rgb(… / …)` derived from those tokens. The masthead is a sticky white `.masthead`: a `.brand-mark` swatch, `#title`, `#status`, and the green primary button `#open-upload` (wired to `surface-tabs.ts::SurfaceTabs.open("upload")`, the same state-machine path as clicking `#tab-upload`). UI type is the system sans stack, with monospace reserved for identifiers, paths, and page geometry; `.pane` trades its drop shadow for a 1px divider plus `--radius` corners, `.page-scroll` is light gray with `.page-stage canvas` carrying its own 1px border and white fill, and a mapped region is blue at rest, deeper on hover, and green when pressed (`aria-pressed="true"`). The two checkboxes on the tab bar stay native `input`s (custom look via `appearance: none` plus a green checked fill), so the e2e `check` / `uncheck` steps are unaffected; every geometry fact above (drawer position and size, fit-width, ratio scrolling, `bottom: 3.5rem`, `max-height: 72vh`) is unchanged.

After fit-width, scroll sync and jumps no longer convert canvas pixels: `scrollFragmentIntoCenter` positions with `(fragment midline pt / page height pt) × container.scrollHeight` clamped to `scrollHeight - clientHeight`, and `syncFrom` derives the midline with `(scrollTop + clientHeight / 2) / scrollHeight × page height pt`; the ±12 pt band, `pickCounterpart`, and the 250 ms suppression are unchanged.

- **upload** (`#panel-upload`): dropping onto `#upload-drop` or choosing through `#upload-file` rejects anything that is not `.pdf`, then `jobs-client.ts::uploadPdf()` posts to `POST /api/uploads` (header `X-Upload-Name`, body is the file bytes); the returned `path` / `workspace` fill `#import-source` / `#import-workspace`, `#upload-status` reads `Uploaded <bytes> bytes · <path>`, and the same submit path as `#import-submit` runs immediately. The path-style form (absolute `source` / `workspace` plus a submit button, disabled with `Import unavailable · API offline` while `apiAvailable` is false) remains: `jobs-client.ts::submitJob()` posts `{"source","workspace"}` — no `viewerDataDir`, which the server defaults to its own `--data-dir`, the directory this viewer reads — then `followJob()` polls `GET /api/jobs/<id>` every 2 s **until the terminal state** (no client-side deadline: a real paper on a real provider runs for minutes, and giving up early strands the reader on the previous revision; while running the status line reads `Job <status> · <id prefix> · <elapsed>`). On `succeeded` it calls `DualPaneReader.load(String(Date.now()))` for an in-place swap onto the job-published revision; a failed swap leaves the previous revision fully intact and shows `Reload failed · …`. On `failed` it shows `Job failed · <stage ?? "fatal"> · <error ≤160 chars>` without touching the reader.
- **select** (`#panel-select`): `GET /api/workspaces` lists the summaries from `discover_workspaces(jobs_root, extra=(the API's own workspace,))` (name / full path / `<committed>/8 stages committed`, where the line reads `<committed>/8 stages committed · degraded` when a stage recorded a degradation / updatedAt / error), and the currently published one is marked `data-current="true"`; a row with `complete === false` or `error !== null` has `Open` disabled. `Open` → `POST /api/workspaces/open` (body `{"workspace": "<absolute path>"}`) → the server's `republish_workspace_viewer()` republishes that workspace's **already-committed artifacts** as a new revision (no stage runs, nothing written into the workspace) → on success `reader.load()` with `Opened · <revision prefix>`. When the API is unavailable the list is cleared and `Workspace list unavailable · API offline` is shown.
- **history** (`#panel-history`): `GET /api/jobs` lists job records newest first by `createdAt` (status / `attempt <n>` / stage / updatedAt / absolute source and workspace paths / the first 160 chars of `error`); a `failed` row gets `Retry` (`POST /api/jobs/<id>/retry` then refresh) and a `succeeded` row gets `Open` (the same republish + `reader.load()` path as select).
- **status** (`#panel-status`): while the panel is open it polls `GET /api/status` every 3 s and renders four lines — API (`API ok · <origin>` on success, i.e. the `GET /api/health` probe passed), worker heartbeat (`Worker running · pid <pid> · <running> job(s) · heartbeat <age>s`, a stale heartbeat reads `Worker stale · last heartbeat <age>s ago`, no heartbeat reads `Worker not detected · start just dev-worker`), job counts (`Queued n · Running n · Succeeded n · Failed n`, extended to `… · Failed n · oldest queued <oldestQueuedAt>` when `queued > 0`), and the viewer publication (`Revision <revision prefix 12> · workspace <workspace ?? "unknown">`, followed by local reader facts: `source n pages` / `target n pages` / `<n> linked regions`, plus `active <node prefix 8>` when a node is selected; `No published revision` when nothing is published). When the API is unreachable only `API unreachable · <status or error>` is shown and the other three lines are cleared.

Requests, status codes, and the read/write boundary of the four new endpoints (`GET /api/workspaces`, `POST /api/workspaces/open`, `POST /api/uploads`, `GET /api/status`) are in [HTTP API](api.en.md); the `<jobs-root>/inbox/` filename rule, the six-key worker heartbeat, and `republish_workspace_viewer`'s "writes nothing into the workspace" contract are in [storage](storage.en.md). `tests/e2e/console-surfaces.spec.ts` covers opening and closing the four surfaces, `API ok` in `#status-api`, a non-empty history list, and `#viewer`'s `data-revision` changing after `Open` in select.

First-page rendering of an import or open swap is still part of candidate preparation: render both panes offscreen and wait for both before committing state and pixels and destroying old PDFs. A getPage or render failure destroys only candidate PDFs, preserving previous reading state and canvases.
