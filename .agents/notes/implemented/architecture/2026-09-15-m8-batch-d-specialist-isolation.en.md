# Agent Note: M8 batch D specialist failure isolation and explicit degradation

Status: implemented

[中文](./2026-09-15-m8-batch-d-specialist-isolation.md) | [English](./2026-09-15-m8-batch-d-specialist-isolation.en.md)

## Problem

The M7 planner routes table-dense documents to a Docling-class specialist ([2026-09-12-m7-parser-ensemble](./2026-09-12-m7-parser-ensemble.en.md)). But `routing.collect_bundles` calls every routed provider in sequence and **any exception bubbles straight up**: `_execute_stage` wraps it in `StageExecutionError`, the Job is marked failed, and the whole document is lost together with the layout/semantic work that had already succeeded. An optional specialist that owns exactly one capability could stop the entire chain.

The second gap is in `evidence/normalize.py`: `merge_evidence_bundles` merges candidates and provenance and **silently discards the member bundles' `issues`**. Even when a provider reports its own failure, no path carries it to `semantic.json`, the viewer's issue list, `metrics.quality_report`, or the benchmark's ERROR count — the failure is unobservable.

Batch D's contract ([`docs/development/m8.md`](../../../../docs/development/m8.md)): a Docling-class failure → TABLE line fallback + Issue, the other document nodes continue, and the document is never marked parse failed. A failure must also not enter the cache (batch C's cache-key semantics).

## Decision

1. **The provider boundary swallows exceptions and `collect_bundles` returns `ProviderCollection(bundles, degradations)`**; `ROUTING_VERSION` → `0.2.0`. Each routed provider is attempted once inside `_attempt`; an `Exception` becomes a `ProviderDegradation(provider, capabilities, substitutes, errorType, message)` instead of propagating. `message` reads `"<ErrorType>: <str(error)>"`, truncated to `MAX_ERROR_MESSAGE_CHARS = 500` (diagnostics are not payload).
2. **Substitution uses only the registry's `Capability.fallback`, never the challenger; each name is attempted at most once per run; substitution does not recurse.** `substitutes` lists only the names that **actually produced a bundle**: when that fallback was already collected for another capability in this run (`table.structure.fallback = mock` while `mock` is the layout primary), it is reused, **never rerun**. A failing fallback gets its own degradation, ordered after the provider it stood in for (one level deep, no chained substitution).
3. **A provider routed for more than one capability set is never silently treated as successful**: `_attempt` caches the failure object, so a second decision reuses the same recorded failure and emits its own degradation instead of concluding "name already attempted".
4. **The Issue is attributed to the failing provider**: `severity` is always `ERROR` (a real provider failure is a defect; WARNING would hide it), `recoverable = true`, `affectedIds = []`, and `id = stable_uuid(document_id, "issue", provider, capabilities, message)` (deterministic, so a rerun never duplicates the Issue). `category` maps the capability onto an **existing** `IssueCategory` (`_CAPABILITY_ISSUE_CATEGORY`: layout.region→LAYOUT_REGION, table.*→TABLE_RECOVERY, formula.*→FORMULA_RECOVERY, scholarly.metadata→SECTION_STRUCTURE, scholarly.bibliography→CITATION_RESOLUTION), falling back to `LAYOUT_REGION` when nothing matches — no new schema enum. `fallback` is `"provider substitution: <names>"` when substitutes exist, otherwise the capability's internal degradation description (`_CAPABILITY_FALLBACK_DESCRIPTION`, e.g. `"table line-row fallback"` for tables, `"front-matter heuristics"` for scholarly.metadata). `fallback` is a member of `Issue.__non_nullable_optional_fields__`, so `None` is never passed explicitly.
5. **`probe.json` gains a `degradations` field** (`[d.to_json() for d in degradations]`, `[]` when nothing failed). The shape is constant and the ad-hoc file stays outside the frozen schemas; `category`/`errorType`/`message` share one source with the Issue.
6. **`StageStatus.DEGRADED` means "artifacts usable, run degraded"**: `commit_stage(..., degraded=True)` writes `"status": "degraded"`, `stage_completed` accepts only COMPLETED, so the **next run reruns that stage** (a failure never becomes a cache hit), while the record itself exists, `_upstream_artifacts` still reads its artifact hashes, and LAYOUT and its downstream stages keep committing. **`WORKSPACE_VERSION` is not bumped**: existing workspaces stay readable (batch C's key-material extension already reruns them once) and degraded is a newly written status; migration/rejection stays with batch E.
7. **`merge_evidence_bundles(bundles, *, issues=())`**: the result's issues are the members' own issues plus the passed-in ones. **The `issues` field is omitted when empty** (`issues` is in `EvidenceBundle.__non_nullable_optional_fields__`, and this keeps an undegraded run byte-identical, so the golden does not move). An empty input still raises `ValueError`.
8. **Folding evidence issues into the `semantic.json` IssueStore is the only channel**: after merging `validate_semantic_recovery`, `_run_semantic_stage` appends the evidence issues, deduplicated by `id`, ordered existing issues → recovery issues → evidence issues. `PIPELINE_VERSION` → `0.2.0`: `pipelineVersion` is a common item of every stage's cache key, and the fold-in logic changed, so existing workspaces must rerun the whole chain once.
9. **Zero bundles is a real failure**: when `collection.bundles` is empty, `_run_evidence_stage` raises `RuntimeError` (message lists every degradation's provider and error) and `_execute_stage` attributes it to `EVIDENCE`. With no evidence authority left, pretending the run degraded successfully would be a lie.
10. **`EvidenceProvider.collect`'s contract is written into its docstring**: it may raise; the router isolates provider failures and substitutes the registry fallback for the lost capabilities.

`fusion.py`, `layout.py`, and `sem_tables.py` are untouched: geometric regions come from `layout.py`'s `page_structure` grouping independently of any provider, and the TABLE line fallback with `confidence.reason == "table fallback: line rows"` has existed since M4 — this batch only makes "the specialist failed" actually reach that path. `schemas/` and the generated bindings are untouched as well.

## Alternatives considered

- **Silently skip a failed provider without an Issue**: that is exactly the gap being fixed — the failure must be observable, otherwise the viewer and benchmark never see the degradation.
- **Resolve substitution recursively (a fallback's fallback)**: one failure would extend the substitution chain indefinitely, and `substitutes` would lose its meaning (who actually produced the bundle?). One level plus name deduplication is predictable.
- **Substitute the challenger**: a challenger is the second-best evidence source for the same capability, not the stand-in after the primary dies; the registry already has a fallback slot for the latter.
- **Add an `IssueCategory` member** (e.g. `EVIDENCE_PROVIDER`): that means changing the frozen schema and regenerating the bindings; the existing categories already express the affected capability.
- **Record a provider failure as WARNING**: it hides a real defect; the sim registry never fails and a real adapter failure is an ERROR.
- **Bump `WORKSPACE_VERSION` to express "a new status value exists"**: it would reject every existing workspace outright, and migration policy belongs to batch E. Old code reading `"status": "degraded"` raises an explicit `unknown stage status`, which is a refusal rather than silent misuse.
- **Record provider failures only in the Job record (batch B's approach)**: `semantic.json` must carry its own issues, otherwise the viewer, the quality report, and the benchmark each need to know what the job recorded.
- **Always write `issues=[]` from `merge_evidence_bundles`**: it would change artifact bytes for undegraded runs too, churning the golden and the benchmark baseline for nothing.
- **Keep accounting a degraded stage as COMPLETED (Issue only)**: the failure would be cached as an outcome and never retried.
- **Treat "already attempted and failed" as success in `_attempt`**: when one provider is routed for two capability sets, the second set would get neither a bundle nor a degradation — a silent failure, the opposite of this batch's goal.

## Consequences

- `pdf_pipeline/routing.py`: `collect_bundles(plan, physical, registry=None) -> ProviderCollection` (no longer `list`); new `ProviderDegradation`, `ProviderCollection`, `issue_category_for_capability`, `fallback_description_for_capability`, `MAX_ERROR_MESSAGE_CHARS`, and two capability maps; `ROUTING_VERSION` `0.1.0` → `0.2.0` (part of the EVIDENCE cache key); `document_model.generated` promoted from `TYPE_CHECKING` to a runtime import (`to_issue` constructs an `Issue`).
- `pdf_pipeline/evidence/normalize.py`: `merge_evidence_bundles` gains a keyword-only `issues`.
- `pdf_pipeline/workspace.py`: `StageStatus.DEGRADED`; `StageRecord.from_json` accepts it; `make_stage_record` / `commit_stage` gain `degraded: bool = False`.
- `pdf_pipeline/pipeline.py`: `PIPELINE_VERSION` `0.1.0` → `0.2.0`; `_run_evidence_stage` uses `ProviderCollection`, writes `probe.json.degradations`, and raises on zero bundles; `_run_semantic_stage` folds in evidence issues.
- `tests/benchmark/run_benchmark.py`: switched to `ProviderCollection` (the sim registry never fails → report byte-identical to the baseline).
- Every call site migrated: `pipeline`, `run_benchmark`, `test_routing`, `test_semantic`; no compatibility shims.
- An existing workspace reruns the whole chain once because `pipelineVersion` changed (expected from batch C), then behaves normally.
- Verification: `test_routing.py` 12 tests, `test_workspace.py` 26, `test_semantic.py` 24, and the new `test_specialist_isolation.py` 3 all green; `just test-python` 523 passed; `just test-golden` (`tests/golden/smoke/semantic.json` unchanged); `just benchmark` exit 0 with an "unchanged" report and an untouched baseline; `just check-fast` green. Observable end to end: table-heavy with a missing Docling dump → the `semantic.json` TABLE is a single-column 9-row fallback (`reason == "table fallback: line rows"`), one `TABLE_RECOVERY` ERROR Issue produced by `docling` (`fallback == "provider substitution: mock"`), `probe.json.degradations[0].substitutes == ["mock"]`, evidence `degraded` and every other stage `completed` in `workspace.json`; on the next run EVIDENCE runs once and LAYOUT not at all. paper-anatomy with a missing GROBID dump → SECTION/PARAGRAPH nodes remain and one `SECTION_STRUCTURE` Issue appears (`fallback == "front-matter heuristics"`). Every routed provider failing → `StageExecutionError` (EVIDENCE) with no `semantic.json` written.
