# Agent Note: M8 Batch F Local Product End-to-End Acceptance

Status: implemented

[中文](./2026-09-16-m8-batch-f-local-e2e.md) | [English](./2026-09-16-m8-batch-f-local-e2e.en.md)

## Problem

[`docs/development/m8.en.md`](../../../../docs/development/m8.en.md) §F requires the PRD §40 product flow — import PDF → analyze → translate → Target PDF → Source/Target jumps — to run end to end on the **running local stack**, and requires "after a publish failure the viewer still reads the previous revision" to be proven at product level, not only as the monkeypatch units in `packages/python/pdf-pipeline/tests/test_rerender_workspace.py`. After batches A–E the stack was: `paper_api` (:8000) + the Vite development server (:4173, the `servePublicData` plugin streams `apps/web/public/data` per request, `/api` proxied to :8000); `paper_worker` existed but nothing booted it except manual `just dev-worker`; the viewer was a read-only fixture reader whose only write path was `POST /api/retranslate`.

Three gaps. First, the product had no import surface: the job API (batch B) could only be fed by curl. Second, even with a submit entry point, the `POST /api/jobs` contract demanded an absolute `viewerDataDir` from the submitter, which a browser cannot know — Vite serves the API process's own `--data-dir`, and a wrong value publishes revisions where nobody reads them. Third, "previous revision survives publish failure" was proven only at unit level: the injection point `_commit_prepared_file` is doc-commented "a seam for publish fault injection", but no env or argument let an external process make a real HTTP publish fail mid-transaction.

## Decision

1. **Import surface = minimal path-style panel, no upload.** `apps/web/src/import-panel.ts` exports `bootImportPanel(reader)`: two text inputs (absolute `source` / `workspace` paths) + submit button + `aria-live` status, calling `POST /api/jobs` → polling `GET /api/jobs/<id>` every 2 s → `reader.load()` on `succeeded` for an in-place revision swap. PRD §40 has no upload; `MAX_BODY_BYTES=4096` and the absolute-path job contract are batch B's foundation, and multipart plus temp-file lifecycles would be a second contract. The client pre-checks only "non-empty and starts with `/`" (the local product is POSIX-only, the same assumption as batch B's `fcntl.flock`); server-side `parse_job_request` validation is unchanged.
2. **New API rule: omitted (or `null`) `viewerDataDir` ⇒ default to the server's own `--data-dir`.** `handle_submit_job` gains keyword `default_viewer_data_dir: Path | None = None`; after `parse_job_request`, `viewer_data_dir = viewer_data_dir or default_viewer_data_dir`; `__main__.do_POST` passes `data_dir`. The 202 response carries the effective directory. Explicit values must still be absolute — the default fills absences, never relaxes validation. Without this rule a browser-submitted job would publish into the runner's `viewer_data_dir=None` default inside the workspace, while Vite streams the API's `--data-dir`: the viewer could never see the new revision.
3. **Worker threading: verified, no code change.** `JobWorker._run_job` already passes `Path(job.viewer_data_dir) if job.viewer_data_dir else None` as the runner's third positional argument; the batch only pins that chain with `test_worker_passes_record_viewer_data_dir_to_runner` (record → runner actual argument).
4. **In-place revision swap: `DualPaneReader.load(revisionBust)`.** Reuses the proven success-path shape of `retranslate()`: `fetchViewerManifest({ cacheBust, fallback: false })` → `loadViewerAssets(…, { includeSource: true })` → assign `meta/model/revision/pdfs` on both sides → both `currentPage=-1`, `setViewerChrome()`, `showPage(0)` on both panes → destroy both previous `PDFDocumentProxy` objects. A candidate-load failure leaves current state byte-untouched and surfaces the error to the caller — no rollback dance, because `manifest.json` is the commit pointer and a failed swap never touches it. `retranslate()` behavior is unchanged.
5. **Publish fault injection = documented env seam: `PAPER_PUBLISH_FAULT=<file name>`.** `pdf_pipeline/config.py` gains `PUBLISH_FAULT_ENV` + `load_publish_fault()` (batch E's `REGISTRY_PATH_ENV` convention); `_commit_prepared_file` compares `target.name` before `staged.replace(target)` and raises `OSError(f"publish fault injected for {target.name}")` on a match. It is configuration-only: not a cache key (it changes no produced bytes), unset ⇒ byte-identical behavior. Env was chosen over a new HTTP endpoint or CLI flag because the seam must fire **inside the publish transaction**, which runs deep in a worker/API process where callers have no function pointer to hand in.
6. **`PAPER_VIEWER_DATA_DIR`: Vite `/data` root override.** The `servePublicData()` data root becomes `process.env.PAPER_VIEWER_DATA_DIR ? path.resolve(env) : path.resolve(publicDir, "data")`; traversal guard, content types, and streaming are unchanged; unset ⇒ byte-identical to before. Its only reason to exist: the fault-path e2e must boot a second real API plus a second Vite over a **copy** of the fixture data without touching the `apps/web/public/data` the main stack serves.
7. **Worker joins `serve-reader`; Playwright serializes.** The local-stack recipe and the playwright `serveCommand` grow to three processes in lockstep (API + worker + vite, `--jobs-root .jobs` pinned on both, comments requiring the strings to stay identical). `fullyParallel: true` → `false` plus `workers: 1`: once a browser-submitted job publishes new revisions into the served data root, `apps/web/public/data` is shared mutable state that other specs read while flipping the manifest, and serialization is the only race-free option. `product-import.spec.ts` adds its own safety: snapshot `public/data` before submitting and restore it byte-for-byte in `finally`, because the later viewer-* specs assert against the anatomy fixture.
8. **The two e2e specs are the product-level counterparts.** `tests/e2e/product-import.spec.ts`: real three-process stack + real lualatex; tikz-vector (a different PDF from the anatomy fixture) enters through the browser, the worker drains the queue, the panel polls `succeeded`, the viewer moves to the job-published revision (`data-revision` changed, target page count ≠ anatomy's), and the both-directions click-jump passes on the new revision. `tests/e2e/publish-failure.spec.ts`: copy the data root + workspace, boot a second API (:8010) with `PAPER_PUBLISH_FAULT=target.pdf`, HTTP `POST /api/retranslate` returns 500 + `publish fault injected`, disk assertions show the manifest, all four stable aliases, and the `revisions/` set **byte-identical to baseline**, then a second Vite (:4183, `PAPER_VIEWER_DATA_DIR` pointed at the copy) boots the viewer on the previous revision and one jump round trip passes. The assertion list mirrors `test_rerender_mid_publish_failure_rolls_back_viewer_and_workspace`; no new invariants were invented.

## Alternatives considered

- **Upload endpoint + temp files**: would need multipart parsing, size/type policy, and cleanup lifecycle, all outside batch B's 4 KB JSON contract; PRD §40 does not ask for it. The path panel is contract-shaped.
- **Panel fills `viewerDataDir` with a guess (e.g. `/`) or asks `/api/health`**: health does not expose the data directory; making the browser guess a path that lands on disk invites silent publishing to the wrong place. The default rule keeps the truth in the one process that knows it (the API's own `--data-dir`), and the 202 echoes the effective value.
- **`load()` copying `retranslate()`'s rollback logic**: `retranslate()` rolls back because the server **already published** and failure happens mid-swap; `load()` can only fail while loading the candidate, before any state moves. Duplicating the try/catch/finally dance for symmetry is unobservable plumbing.
- **Fault injection as `POST /api/debug/publish-fault`**: adds an endpoint that can deliberately break publishing to a production API — pure attack surface; the env seam exists only in processes that explicitly set it.
- **Fake worker/runner in the e2e**: §F's acceptance object is the real chain (queue, flock, lualatex, publish transaction); a fake runner proves only what the units already prove.
- **Keep e2e parallel with per-spec data roots**: per-spec roots would mean making `servePublicData` switchable per request (complicating the main stack) or one three-process stack per spec (ports/resources doubled). Serial + snapshot-restore is minimal and sufficient; the race's root cause (a shared mutable publish target) is part of the feature being tested.
- **Key `PAPER_PUBLISH_FAULT` into the stage cache**: it changes no bytes of any successful publish (a hit means nothing was published); keying it would make fault debugging itself invalidate caches.

## Consequences

- `packages/python/pdf-pipeline/src/pdf_pipeline/config.py`: new `PUBLISH_FAULT_ENV`, `load_publish_fault()`; module docstring widened to "operator environment configuration (batches E and F)".
- `packages/python/pdf-pipeline/src/pdf_pipeline/pipeline.py`: `_commit_prepared_file` checks the seam (+2 lines); import adds `load_publish_fault`. With the env unset the publish path is byte-for-byte unchanged — every existing `test_rerender_workspace.py` case passes unmodified, which is the proof.
- `apps/api`: `jobs.py` `handle_submit_job` gains `default_viewer_data_dir`; `__main__.py` passes `data_dir`.
- Python tests: `test_parser_config.py` +3 (unset/empty/read env); `test_rerender_workspace.py` +3 (seam fires inside `_replace_files_with_rollback` with already-replaced aliases restored, manifest fault restores pre-existing files and never creates the manifest, `_publish_viewer_revision` fault keeps the previous revision byte-identical and removes the staged `revisions/<id>/`); `test_job_worker.py` +1 (record → runner third positional). Header gains `reportPrivateUsage=false` (matching `test_job_worker.py`).
- `apps/web`: `reader.ts` new `load()`; new module `import-panel.ts` (+ `import-panel.test.ts`, 6 cases: offline disables submit, submit body `{source, workspace}`, poll-to-succeeded calls injected `load` exactly once, failed record renders stage/error without swapping, reload failure keeps the previous revision, relative paths never touch the API); `index.html` toolbar `#import-panel` form; `viewer.css` panel styles; `main.ts` calls `bootImportPanel(reader)` after `reader.start()`.
- `apps/web/vite.config.ts`: `servePublicData` data root reads `PAPER_VIEWER_DATA_DIR`.
- `justfile` `serve-reader` and `playwright.config.ts` `serveCommand`: three processes; `fullyParallel: false` + `workers: 1`.
- `tests/e2e/`: new `product-import.spec.ts`, `publish-failure.spec.ts`.
- Docs: `docs/architecture/api.en.md` (submit-body default rule), `reader.en.md` (import panel flow, `load()`, `PAPER_VIEWER_DATA_DIR`, worker in the stack), `storage.en.md` (publish-transaction paragraph names `PAPER_PUBLISH_FAULT`), `docs/development/m8.en.md` §F landed paragraph, roadmap + README status lines; Chinese primaries updated alongside.
- Observed behavior: `just test-e2e` green across all seven specs; the manual stack smoke showed `POST /api/jobs` (no `viewerDataDir`) returning `"viewerDataDir":"apps/web/public/data"`, the worker finishing `succeeded`, and :4173's manifest flipping to the new revision.
- Left open: no separate human browser acceptance (panel UX polish); every interaction path is covered by e2e. A stale manual worker under `reuseExistingServer` double-claims nothing — flock serialization keeps results deterministic either way.
